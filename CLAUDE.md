# Derangiquarium — Architecture Doc

This file is the source of truth across phases. Each phase may be a fresh session — read this before writing code, and update the "Current Phase" section at the end of every phase.

## Vision

Insaniquarium, but the tank is one giant continuous world with a factory grid at the bottom. Top of the tank: classic feed-fish-watch-them-grow-and-drop-loot loop. Bottom of the tank: a player-built seabed grid (ramps, blasters, collectors) that automatically routes falling coins/waste/science into the right processor — a Blaster can even launch something back up into the water column instead of collecting it. Between the two: power (Electric Eels), tank toxicity/cleanliness, cybernetic gear crafted for individual fish, and — once Gene-Splicing is researched — dragging a utility fish onto another fish to breed a dual-role hybrid. Progression itself is diegetic: a Mound sitting on the seabed cracks open in stages as the player throws money at it, revealing each new tier of mechanics (see Tier Progression & The Mound below) rather than unlocking silently through a menu.

Arc of a level: manual and frantic → hands-off and humming.

**This is a campaign game, not a sandbox.** Levels are discrete and their state is wiped on transition. Meta progression (tech, unlocked buildings/species, completed levels) persists forever via LocalStorage. This split is architectural — see State Shape below — and exists from Phase 1 even though nothing persists yet until Phase 5 wires up save/load.

## State Shape & Field Ownership

Root state is one plain object, fully JSON-serializable — no class instances, no DOM refs, no closures, no `Map`/`Set` in any serialized path. Plain objects/arrays only.

```js
state = {
  meta: {                    // persists across levels, saved to LocalStorage (wired in Phase 5)
    scienceTotal,            // number — written by Systems.js (Phase 4)
    techUnlocked: [],        // string[] of tech ids — written by UI.js tech tree (Phase 4)
    buildingsUnlocked: [],   // string[] of grid tile ids — written by Levels.js on level completion
    speciesUnlocked: [],     // string[] of species ids — written by Levels.js on level completion
    levelsCompleted: [],     // string[] of level ids — written by Levels.js
    settings: {},            // sound toggle etc — written by UI.js (Phase 5)
  },
  level: {                   // wiped and rebuilt by Levels.js on every level load — nothing else may reset this
    levelId,                 // string — set once on load by Levels.js
    money,                   // number — written by Entities.js (coin bank) and UI.js (shop spend)
    cleanliness,             // number 0-100 — written by Systems.js (Phase 3), read by Entities.js for stress
    powerSupply, powerDemand,// numbers — written by Systems.js (Phase 3)
    entities: [],            // Fish/Alien instances (plain data) — written by Entities.js
    items: [],                // Food/Coin/Waste/Science instances (plain data) — written by Entities.js, read/moved by Grid.js
    floatingTexts: [],        // transient "+$N" pickup readouts (plain data) — written by Entities.js, rendered by main.js; not physics items, Grid.js never touches these
    grid,                     // full WORLD_TILES_H x WORLD_TILES_W tile-id array (Phase 2) — written by Grid.js only; rows above SEABED_ROW_START always stay TILE_EMPTY
    gridStats: { itemsRoutedTotal }, // lifetime count of items a Collector tile has consumed (Phase 2) — written by Entities.js on consumption, read by main.js/UI.js for the items-routed-per-minute debug stat
    tier,                     // number 1-4 (Phase 2) — Mound-driven progression, written by Mound.js's crackMound(); level-scoped like everything else here, resets to 1 on every level load/restart even though the meta-unlocks a previous crack granted stay permanent
    moundTeased,               // bool (Phase 2) — has the Mound's first (fake, no-op) crack attempt already happened this level? written by Mound.js's crackMound()
    notifications: [],        // rolling ticker log (Phase 2) — { id, text, elapsed }, written by any system with something to announce (Mound.js, Entities.js so far), read/rendered by UI.js, capped at NOTIFICATION_LOG_MAX
    tankPoints: { total, available }, // Phase 2 — earned by Entities.js on fish adult-growth transitions, spent in UI.js's Tank Upgrades panel; level-scoped, not meta — see CLAUDE.md's "Tank Points & Tank Upgrades"
    upgrades: { foodQuality, fishMovement, foodCapacity }, // Phase 2 — purchased Tank Upgrade levels (0 = not bought), written by UI.js's panel, read live by Entities.js
    waveTimer,                // number — written by Systems.js (Phase 5)
    elapsed,                  // number, ms since level start — written by Engine.js sim loop
  },
  camera: { x, y, zoom },     // written by Engine.js only; zoom is auto-fit to the water column height by main.js on load/resize
  ui: { selectedTool, shopCollapsed, tankPanelCollapsed, paused }, // selectedTool: which click-tool a canvas click performs (e.g. 'food'); shopCollapsed/tankPanelCollapsed/paused: toggled by UI.js (shop button/S key, tank button/P key, Escape/pause menu) — paused is read by main.js's update() to freeze the sim entirely; opening one of the two side panels auto-collapses the other
  debug: { ... },              // overlay toggles, time scale, selected species for G key — written by Engine.js/UI.js
}
```

**Rule:** any system that writes to `state.level` when it means `state.meta` (or vice versa) is a bug. This is called out with a comment at every level-load/reset site.

## SPECIES table schema & behavior tags

Species are data rows in `Config.js`, not subclasses. A single `Fish` entity in `Entities.js` is driven by a `SPECIES` table lookup keyed by species id.

Each `SPECIES` row provides:
- `id, name, tier, cost, description`
- `swimSpeed, hungerRate, growthStages[]` (each stage: `{ scale, dropInterval, dropValue, feedsRequired }`), `lifespan`
- `behavior: []` — array of behavior tags (composable)
- `dropType` — item type produced (e.g. `'coin'`, `'waste_cleared'`, `'power'`, `'science_blue'`)
- `unlockedByDefault: bool` — Tier 1 base species are `true` in Phase 1; every other row is scaffolded with `false` until its phase/mechanism grants it (see Species Roster below)
- `parents: [id, id]` — **hybrids only.** The two base species this one is spliced from; absent on all 6 base species. Phase 4's Gene-Splicing UI will use this to look up "what do these two produce," but nothing reads it before then — it's scaffolding, not behavior.

Behavior tags (composable, reused across species):
- `FEEDER` — eats food, drops items on a timer scaled by growth stage
- `SCAVENGER` — eats waste, drives tank cleanliness (Phase 3)
- `GENERATOR` — produces power (Phase 3)
- `RESEARCHER` — produces science near a Hub (Phase 4)
- `HUNTER` — attacks aliens *(not currently assigned to any species — held over from an early draft; Phase 5+ combat direction is undefined pending a future design pass, see Species Roster below)*
- `GRID_WALKER` — moves on seabed tiles rather than swimming *(also currently unassigned, same caveat)*

A hybrid's `behavior` is simply the union of its two parents' tags (e.g. Suckerfish `['SCAVENGER']` + Electric Eel `['GENERATOR']` → Scrub-Eel `['SCAVENGER', 'GENERATOR']`) — the Fish entity doesn't need to know a species is a hybrid at all, it just reads whatever tags are in the row.

Adding a species = adding one `SPECIES` row + at most one small behavior function. Never a new class.

## Species Roster & Progression

**6 base species, 12 hybrids, 18 total.** No standalone tier ladder beyond that — the old draft's separate Tier 2/3/4/exotic species (Voltminnow, Bristle Crab, Lumenjelly, Cogwhelk, Lancefish, Blasterpuff, Deepstalker, Prism Guppy, Magnetfish) are cut from the roster as of this revision. This section is the current source of truth for who exists; ignore any species list in the original planning prompt that conflicts with it. (Terminology note: this old "tier ladder" and each `SPECIES` row's numeric `tier` field predate, and are unrelated to, the Tier 1-4 Mound progression introduced below in Tier Progression & The Mound — that one is capitalized "Tier" throughout this doc to keep the two apart.)

**The 6 base species:**
| Species | Role | Behavior tag |
|---|---|---|
| Guppy | Baseline feeder | `FEEDER` |
| Dartfin | Fast, cheap feeder | `FEEDER` |
| Blimpfish | Slow, expensive feeder | `FEEDER` |
| Suckerfish | Scavenger / cleanliness | `SCAVENGER` |
| Electric Eel | Power generator | `GENERATOR` |
| Science Octopus | Researcher | `RESEARCHER` |

**Gene-Splicing:** once researched (Phase 4 Science Tech Tree), the 3 utility fish (Suckerfish, Electric Eel, Science Octopus) can be dragged onto any other base fish — including onto each other — to splice a dual-role hybrid. That's `3 × 5` ordered target pairs, but a Suckerfish+Eel splice is the same resulting hybrid regardless of which one gets dragged onto which, so the 3 utility-onto-utility pairs only count once each: `(3 utility × 3 feeders) + C(3,2) utility-utility = 9 + 3 = 12` unique hybrids. The 3 feeder-only pairs (Guppy+Dartfin, Guppy+Blimpfish, Dartfin+Blimpfish) aren't valid splices — neither side has a utility role to contribute.

**Splicing requires an adult target, and a feeder-based hybrid's coin value is derived from it:** a utility fish can only be dragged onto a base fish that has already reached its final (adult) growth stage — not a hatchling or juvenile. For the 9 feeder-based hybrids (a utility fish spliced onto Guppy/Dartfin/Blimpfish), the resulting hybrid's `dropValue` is fixed at 1.2x whichever feeder parent's *adult* `dropValue` was at the moment of splicing — e.g. Scrub Guppy/Volt Guppy/Scholar Guppy all carry `dropValue: 6` (1.2x Guppy's adult value of 5) regardless of which utility fish was used, since the utility parent only determines the secondary behavior tag, not the coin payout. This doesn't apply to the 3 utility-utility hybrids (Scrub-Eel, Scrub-Topus, Volt-Topus) — neither parent is a feeder, so there's no adult coin value to inherit from; their `dropValue` is unchanged from their original (mostly non-monetary) scaffold values. None of this gating is actually implemented yet (Phase 4 hasn't built the drag-to-splice interaction — see Phase rollout below), but the target `dropValue`s already reflect it in `Config.js` so the numbers don't need retuning once that interaction exists.

Hybrid naming/tag pattern (see `parents` field above): `Scrub` prefix = inherits `SCAVENGER`, `Volt` prefix = inherits `GENERATOR`, `Scholar` prefix = inherits `RESEARCHER`; a feeder-based hybrid is `[Prefix] [FeederName]`, a utility-utility hybrid is `[Prefix]-[OtherUtilityName]` (e.g. `Scrub-Eel`, the one name given directly in the design update).

**Phase rollout:** describes when Claude *codes* each species/mechanic. See the new Tier Progression & The Mound section below for when the *player* actually unlocks them within a level — Phase and Tier are different axes (Phase = build roadmap, Tier = in-level narrative progression) that now interlock: the Mound's Tier-crack action is what mechanically grants a meta unlock, even in a phase before that species'/building's full behavior is wired up.
- **Phase 2 (current):** grid/routing work, plus the Mound itself and the Tier 1 -> Tier 2 crack (see below) — cracking it grants Suckerfish and the 5 base buildings into `state.meta`, but Suckerfish still has no real SCAVENGER behavior yet (that's Phase 3) and just swims around inert if spawned, same as it was as pre-Mound scaffold data.
- **Phase 3:** Suckerfish's real Scavenger behavior (eats waste, drives cleanliness/toxicity) and Electric Eel (Generator role, power grid) — wired to fire alongside the Mound's existing Tier 2 -> Tier 3 crack (cost already defined in Phase 2's `Config.js`, but nothing currently listens for reaching Tier 3 besides granting the Electric Eel unlock). Also where the Tier 2 "basic buildings are dirty" downside (waste-on-consume, already spawning as of Phase 2) actually starts *mattering* — real toxicity math turns that waste into a cleanliness cost, and Electric building variants (Electric Collector, Auto-Feeder) that skip it need to exist.
- **Phase 4:** Science Octopus unlocks (Researcher role) alongside the Science Tech Tree, tied to the Mound's Tier 3 -> Tier 4 crack — which is also when it shatters completely and reveals the Science Lab (see below). Gene-Splicing itself is a tech node purchased with Science inside that Lab's tech tree UI — researching it is what turns on the drag-a-utility-fish-onto-another-fish interaction and makes the 12 hybrid rows spawnable.
- **Phase 5+:** undefined pending a future design pass. The original plan's alien-wave/combat content (Lancefish, Blasterpuff, Deepstalker, `HUNTER` tag) is not part of the current roster; don't build toward it without new direction.

**Building unlock rule:** superseded by the Mound below — see that section for the live mechanism. `state.meta.buildingsUnlocked`/`speciesUnlocked` are still the persistent unlock flags (`getAvailableBuildings`/`getAvailableSpecies` in `Levels.js` still gate the shop off both these and each level's `allowedBuildings`/`allowedSpecies` allow-list, unchanged), but they're now written by `Mound.js`'s `crackMound()` instead of "on level completion" (that old mechanism was never actually implemented, and is retired in favor of the Mound). Gene-Splicing still unlocks manually by spending Science in the Phase 4 tech tree (`state.meta.techUnlocked`, written by `UI.js`'s tech tree) once the Tier 4 Science Lab is reachable.

## Tier Progression & The Mound

Every level starts with a large, uncracked Mound sitting at the bottom-center of the seabed grid (`Mound.js`, `MOUND_X = WORLD_W / 2` in `Config.js`). The camera itself starts at world x=0 (the far-left edge) via `Levels.js`'s `loadLevel`, so without help the Mound would sit ~2000px off the right edge of the screen at level start — `Mound.js`'s `centerCameraOnMound(camera)` re-centers `camera.x` on `MOUND_X` (clamped to the world's bounds), called once by `main.js` right after the initial zoom/viewWidth computation and again by `UI.js`'s `restartLevel` after every restart (both paths go through `loadLevel`, which resets `camera.x` to 0). Deliberately not called from the window-resize handler, so resizing the browser mid-play doesn't yank the camera back to the Mound once the player has panned elsewhere. It's the diegetic replacement for "buildings unlock automatically" — instead, the player clicks the Mound and throws money at it, which advances `state.level.tier` (1-4, level-scoped like everything else in `state.level` — a restarted or new level always starts back at Tier 1, even though the meta-unlocks a previous crack already granted stay permanently available per the usual meta/level split). This is a different axis from *Phase* (Phase = how much of the game Claude has built so far; Tier = how far the player has progressed within the current level's arc) — see the note at the top of Phase rollout above.

**The four tiers:**
1. **Tier 1 (level start):** only feeding and manual coin collection. The Mound sits there uncracked, 10% bigger than its original size (`MOUND_WIDTH_TILES`/`MOUND_HEIGHT_PX` in `Config.js`) — clicking it opens a small popup right above it ("Throw money at it" / a `$`-labeled button showing `getMoundNextCost(state)`, disabled and grayed out like the shop's Buy button when unaffordable / a Cancel button) — see "The tease" below for what the first click at this popup actually does. This replaced an earlier version of the Mound that cracked immediately on click with a persistent on-canvas "Throw $X at it" label and no popup at all — the user explicitly asked for a real popup here, overriding this project's general no-extra-confirmation-modals preference (which still applies elsewhere, e.g. the shop) — and then, after seeing a first pass that centered/dimmed the whole screen pause-menu-style, asked for it un-dimmed, smaller, positioned right next to the Mound, and flying out of/back into it. `UI.js` owns it (`openMoundMenu`/`closeMoundMenu`/`isMoundMenuOpen`): `#mound-overlay` is a fully transparent, full-viewport click-catcher (so clicking outside the card still closes it, just with no visible tint); `#mound-menu-anchor`'s `left`/`top` are set every render frame it's open (`updateMoundMenuPosition`, via `worldToScreen(MOUND_X, ...)`) so the popup tracks the Mound's screen position even if the camera pans while it's open, with a static `translate(-50%, -100%)` anchoring the anchor's bottom-center there; `#mound-menu` itself carries a separate `transform: scale()` + opacity CSS transition, pivoting from that same bottom-center (`transform-origin: 50% 100%`), toggled by a `.mound-menu-closed` class — opening forces that class on then strips it next paint (the same forced-reflow trick `playMoneyFlash` uses) so the grow plays from a standing start, closing adds it back and defers actually hiding the overlay by `MOUND_MENU_TRANSITION_MS` so the shrink is visible first. The popup doesn't freeze the sim (`state.ui.paused`) — it's a lightweight decision popup, not a full pause state, same as the shop staying live while open. Escape closes it first if it's open, rather than opening the pause menu on top of it (see `main.js`'s keydown handler).
2. **Tier 2 (rudimentary factory, dirty):** grants the 5 base buildings (Wall, Ramp Left/Right, Collector, Blaster) and Suckerfish into `state.meta`. Downside: every basic building is unpowered and "dirty" — consuming an item also spawns a Waste item as a byproduct (Phase 2 scaffold: a basic Collector banking a coin also spawns waste at the same spot; see `Config.js`'s `WASTE_*` constants and `Entities.js`). Nothing currently *consumes* waste or turns it into a real cleanliness cost — that's Phase 3 (Suckerfish's real behavior + toxicity math). For now it just piles up on the seabed as visible pressure to get there. The Blaster is the one Tier 2 building that isn't dirty by nature — it doesn't *consume* an item at all, just relaunches it (see below), so it never spawns Waste.
3. **Tier 3 (electrification, clean automation) — Phase 3 alignment, not yet built:** grants Electric Eel. Electric building variants (Electric Collector, Auto-Feeder — exact placement/UI for Auto-Feeder still undecided, since it's arguably a water-column apparatus rather than a seabed tile) require power from Electric Eels and do **not** spawn Waste when processing an item — the dirty byproduct moves from the machinery to the Eels themselves (their own feeding/upkeep is where that cost lands instead, mechanism TBD in Phase 3). None of this tier's buildings exist in code yet; only the Mound's Tier 2 -> 3 crack cost and the Electric Eel meta-unlock are wired up so far.
4. **Tier 4 (the reveal) — Phase 4 alignment, not yet built:** the Mound shatters completely instead of cracking further, revealing the Science Lab underneath. Clicking the Lab (not the Mound — it's a different clickable once revealed) opens the Tech Tree UI, granting Science Octopus and the Gene-Splicing research option. `Mound.js`'s render/click functions already no-op once `state.level.tier >= MOUND_MAX_TIER`, leaving a deliberate gap for Phase 4 to draw the Lab in its place.

**The tease:** the very first "throw money" attempt at the Mound, ever, is a red herring — it costs `MOUND_TEASE_COST` ($150) but does **not** advance the tier at all, just spends the money and posts "That didn't seem to do anything. Maybe I should try more money." to the notification ticker. `state.level.moundTeased` (set `true` the moment this fires) is what the game reads to tell "still need the joke attempt" from "already teased, next attempt is the real Tier 1 -> 2 crack" — both are the same click/popup/button, the *cost and outcome* are just conditional on that flag (`Mound.js`'s `getMoundNextCost(state)`). It resets to `false` on every level load/restart same as everything else in `state.level`, so the joke replays each fresh playthrough.

**Mechanism (`Mound.js`):** `MOUND_CRACK_COST` in `Config.js` is a plain `{ tier: cost }` map — `{1: 1000, 2: 5000, 3: 25000}`, the *real* cost to crack from that tier once teased (placeholder balance, tune once real playtesting exists, same as every other economy constant; Tier 3 -> 4 is priced steeply on purpose — "they gotta make a whole system first to unlock tier 4," per the design note, even though nothing beyond money actually gates it yet). `getMoundNextCost(state)` is the single source of truth `UI.js`'s popup button reads for its label/afford-check — it returns `MOUND_TEASE_COST` while `tier === 1 && !moundTeased`, otherwise `MOUND_CRACK_COST[tier]`. `TIER_UNLOCKS` maps a tier to the `{ species: [...], buildings: [...] }` ids it grants; `crackMound()` spends whatever `getMoundNextCost` returned, and either (a) just sets `moundTeased` and posts the joke line, or (b) increments `state.level.tier`, pushes those ids into `state.meta.speciesUnlocked`/`buildingsUnlocked` (deduped), and writes the real crack's narrative line — see which branch based on the same `moundTeased` check. `Tier 3`/`4` already have their species listed in `TIER_UNLOCKS` even though their buildings/mechanics aren't coded — reaching them today just makes Electric Eel/Science Octopus/the hybrids purchasable early with no real Generator/Researcher/splicing behavior behind them yet, same inert-scaffold situation every not-yet-behavior-wired species has always been in.

**The Blaster:** the tile that replaced Funnel and Vacuum Pipe (cut for being "technically works but functionally useless" — they moved items around without creating any interesting outcome). A Blaster is solid: an item lands on it like a Wall, but instead of resting, `Grid.js`'s `handleLanding` immediately fires it back up (`launchFromBlaster`). Launch height is `BLASTER_LAUNCH_MIN_FRACTION` (50%) of the tank's height at the shallowest possible placement, rising toward `+ BLASTER_LAUNCH_MAX_DEPTH_BONUS` (15%) the deeper into the city it's placed, maxing at 65% of the tank's height for a Blaster on the very bottom row — always comfortably inside the water column. The speed needed (`v = sqrt(2 * gravity * height)`) is computed from the item's own gravity constant, so a coin and a future slower-falling item arc differently. The shot isn't purely vertical any more: it's split into vx/vy components by an angle up to `BLASTER_LAUNCH_ANGLE_MAX_DEG` (7°) off vertical, based on exactly where within the tile's width the item was when it landed (`item.x` relative to the tile's center, linearly mapped) — dead-center launches straight up, a hit near the left/right edge tilts that far toward that side, at the same total speed either way (only the direction changes, not the magnitude). This is why `Entities.js`'s `updateCoin`/`updateWaste` now integrate `item.x += item.vx * dt` in their open-water branch too (previously they only ever touched `item.y` there — nothing before this ever gave a coin/waste a nonzero `vx` while above `SEABED_FLOOR_Y`, so the angled launch would've had zero visible effect without this, since most Blaster shots leave the seabed band entirely during their arc). No new physics states are needed for the rise itself: a large negative `vy` just decelerates back through 0 and into a normal fall via the exact same gravity integration already used everywhere else — including, if nothing intercepts it, falling back down (usually not onto the *exact* same spot any more, since an off-center hit drifts sideways during the arc) and potentially relaunching again if it lands back on a Blaster, which is intentional (an oscillating fountain, not a bug) since it keeps giving the player (or eventually a fish) another chance to interact with whatever's inside. Rendered with a slightly rounded top (`BLASTER_TOP_CORNER_RADIUS_FRACTION`, bottom stays square) so the launch end reads visually distinct from a plain block.

**Ramps ("funnels"):** a Ramp doesn't arrest vertical motion at all, in either direction — this replaced an earlier version where landing on a Ramp set an `item.slidingRamp` flag and rode a fixed-speed 45-degree diagonal slide (`RAMP_SLIDE_SPEED`) until it reached the next solid tile, which read as a sticky conveyor belt rather than something that just deflects what's already moving through it, per direct feedback ("it's not a sticky conveyor belt, its like a mini fan"). Ramps are deliberately excluded from `Grid.js`'s `SOLID_TILES` set — `sweepVertical` never "lands" an item on one, so an item falling *or rising* (e.g. off a Blaster) through a Ramp's row keeps its `vy` completely untouched. Instead, `applyRampNudge` (called every sub-step of `sweepVertical`, not just once per tick, so a fast-moving item can't skip over an entire row within one tick) checks whether the item's current row is a Ramp tile and, if so, shifts its `x` by exactly one `RAMP_NUDGE_DISTANCE` (one tile width) in that Ramp's direction — once per row, tracked via `item.rampNudgedRow` so a slow-moving or lingering item doesn't get re-nudged every tick it happens to still be passing through the same row (that would read as stuttering, not "moved one tile"). `rampNudgedRow` clears the moment the item leaves that row, so a second Ramp of the same direction placed immediately below/above the first legitimately chains the push further — that's not specially blocked. Rendered as a triangle pointing the direction it nudges (`Grid.js`'s `renderTileShape`) rather than a plain square, so the effect reads at a glance: a left-pointing wedge for Ramp Left, right-pointing for Ramp Right.

**The Collector:** no longer banks a coin the instant it lands — `Grid.js`'s `handleLanding` starts a hold instead, returning a `'processing'` status (see `stepItemOnGrid`'s status list) rather than `'consumed'` right away. `stepCollectorProcessing` runs every tick an item is mid-hold: it eases the item toward the tile's stored center (`COLLECTOR_PULL_STRENGTH`, an exponential approach so an off-center landing visibly glides in rather than snapping into place) and counts up toward `COLLECTOR_PROCESS_DURATION_MS` (3000ms) before finally reporting `'consumed'`. While processing, the item's `mass` is temporarily overridden to `COLLECTOR_PROCESSING_MASS` (1000, restored once consumed or interrupted) so it barely budges under `resolveItemCollisions` if something else piles into it mid-hold — reusing the existing mass-weighting system rather than needing to special-case it out of collision resolution entirely, which also means new arrivals visibly bank up around it instead of overlapping it. If the Collector tile itself gets torn down mid-process, `stepCollectorProcessing` notices (`tileAt` on the stored center no longer reports `TILE_COLLECTOR`) and hands the item back to normal falling physics with its real mass restored, rather than leaving it frozen forever at a now-empty spot. Rendered with a circle in the tile's center (`COLLECTOR_CIRCLE_RADIUS_FRACTION`, `Grid.js`'s `renderTileShape`) — the point everything actually gets drawn into. Verified this survives realistic collision pressure, not just an isolated item: a direct Node sim with one coin guaranteed to land on the Collector plus 15 more scattered across a wide wall strip around it (staggered arrival, mimicking a busy swarm) still consumed the guaranteed coin at almost exactly 3000ms, having drifted less than half a pixel from its landing spot the entire time.

**Waste (Phase 2 scaffold):** a third item type alongside food/coin (`Entities.js`'s `createWaste`), reusing the exact same `Grid.js` tile physics as a coin (falls, lands on tiles, can be routed) but isn't click-bankable and nothing currently consumes it — it just accumulates. Spawned by `Entities.js` (not `Grid.js` — `stepItemOnGrid` returns `'falling'`/`'resting'`/`'processing'`/`'consumed'`/`'lost'`, see that function's own comment for the current contract) whenever `updateCoin`/`updateFood` see `'consumed'` come back, which today can only mean a plain `TILE_COLLECTOR` finished its processing hold — the only tile that reports it. Once an Electric Collector exists (Tier 3) this call site will need to branch on which tile actually consumed the item before deciding whether to spawn Waste.

## Rolling Notification Log

`state.level.notifications` — a capped array (`NOTIFICATION_LOG_MAX` in `Config.js`, oldest entries drop off past that) of `{ id, text, elapsed }`, rendered by `UI.js` as a collapsible ticker in the HUD (top-left, collapsed by default to its latest line; click to expand a scrollback of recent messages). Two systems write to it so far: `Mound.js` (the tease's joke line, and each real crack's narration) and `Entities.js` (the one-time Tank Points tutorial line — see Tank Points & Tank Upgrades below). The intent per the design updates is for this to also carry gameplay alerts (cleanliness warnings, wave warnings) and system status (power grid) once Phase 3+ systems exist to write them; any system can push a `{ text }` onto `state.level.notifications` (capped the same way, see either writer for the pattern) and the ticker picks it up with no changes needed on its end.

## Tank Points & Tank Upgrades

A second, separate progression currency alongside money and Tier — earned automatically, not spent on the shop's fish/buildings, only on a dedicated upgrade panel. `state.level.tankPoints = { total, available }` — level-scoped like Tier and everything else in `state.level` (a restart wipes both back to 0, same as purchased upgrade levels), not `state.meta`: this is deliberately a per-playthrough resource, not a permanent unlock currency like species/buildings. `total` never decreases (lifetime-earned this level, in case a later phase wants it for stats); `available` is what purchases spend.

**Earning:** `Entities.js`'s `awardTankPoint()` fires exactly once per fish — the moment its growth `stage` transitions into that species' final `growthStages` index (checked as `wasAdult`/`stage === growthStages.length - 1` around the existing feed-driven stage-advance in `updateFish`, the only place growth already happens). Cheat-spawning an already-grown fish (`Shift+G`, or `grown: true` generally) never triggers this — it starts at the adult stage rather than transitioning into it, so there's no exploit. Every award spawns a small `+1 Tank Point!` floating text over the fish (`TANK_POINT_COLOR` in `Config.js`); the very first one *also* posts a one-time explanatory line to the notification ticker ("...that's your first Tank Point! Spend Tank Points in the Tank Upgrades panel...") so a player who's never seen the mechanic before understands what just happened and where to spend it — gated on `state.level.tankPoints.total === 0` at the moment of the award, so it can only ever fire once per level.

**The panel:** `UI.js` owns a Tank Upgrades side panel, structurally the shop's twin — same collapse/expand behavior, same card styling — opened via a dedicated button (🏆) directly below the Shop's own collapse button in a shared always-on-top `#panel-toggle-cluster` (both toggle buttons live there now, outside either panel's own box, so neither panel's expand/collapse state can ever visually cover the other's button — see the CSS comment on `#panel-toggle-cluster`). Opening either panel auto-closes the other (`UI.js`'s `toggleShopCollapse`/`toggleTankPanel` each collapse the other before expanding themselves) — the two side panels share the same on-screen slot (`top:14px;right:14px;bottom:14px`), so at most one is ever expanded. `P` is the Tank panel's hotkey, mirroring `S` for the shop. Whichever of the two toggle buttons corresponds to the currently-open panel gets a `.panel-toggle-active` class (a filled ring + darker background, toggled in `updateShopCollapse`/`updateTankPanelCollapse`) — both buttons stay visible and, without this, identical-looking regardless of which panel is actually open, which per direct feedback wasn't obvious enough at a glance.

Each card's description line is deliberately pure stats, current level in red → next level in green (e.g. "Food fills 55 hunger → 65 hunger, sinks 0% slower → 10% slower") — no framing about design intent ("restores original speed," "deliberately reduced," etc.) leaks into player-facing panel text, even though that framing is exactly how the mechanic is described below and in `Config.js`'s comments for developers. `UI.js`'s `describeFoodQualityLevel`/`describeFishMovementLevel`/`describeFoodCapacityLevel` return small HTML strings (`.stat-current`/`.stat-next` spans) set via `innerHTML`, not `textContent` — safe here since every value going in is a computed number, never user input.

**Costs:** all three purchasable trees share one cost curve, `TANK_UPGRADE_COSTS = [2, 5, 15, 30, 50]` in `Config.js` (`FOOD_QUALITY_UPGRADE_COSTS`/`FISH_MOVEMENT_UPGRADE_COSTS`/`FOOD_CAPACITY_UPGRADE_COSTS` are all just aliases of it) — a much steeper 5-level ladder than the original flat `[1,2,3,4]`, per direct feedback that upgrades felt too cheap/quick to max out. Going from 4 levels to 5 meant `FOOD_HUNGER_RELIEF_BY_LEVEL` needed a 6th entry (index 0 = unupgraded through index 5 = level 5, now `[55, 65, 75, 85, 100, 115]`); Fish Movement's and Food Capacity's per-level effects are pure `constant × level` formulas, so they extended to level 5 automatically with no separate table.

**Upgrade scope (four cards, the three purchasable ones level-gated — must own level N-1 to buy level N):**
- **Food Quality** (`state.level.upgrades.foodQuality`, 0-5, costs `FOOD_QUALITY_UPGRADE_COSTS`): each level (a) looks up a flatter, larger hunger-relief amount from `FOOD_HUNGER_RELIEF_BY_LEVEL`, replacing the old dynamic `FOOD_HUNGER_RELIEF_FLAT + FRACTION*hunger` formula entirely — applied in `updateFish`'s eat branch with the hunger-floor clamp removed, so a higher-quality feed than the fish actually needed pushes hunger *negative* (an "overfed" state Entities.js leaves inert for now — no bonus reads it yet, a hook for a later phase), and (b) reduces food's fall speed by `FOOD_QUALITY_SINK_SPEED_REDUCTION_PER_LEVEL` (10%, doubled from an original 5% as part of a general slower-pacing pass) per level, scaling both `FOOD_GRAVITY` and `FOOD_MAX_FALL_SPEED` together, applied live in `updateFood` (reads `state.level.upgrades.foodQuality` every tick, not baked into a pellet at spawn time).
- **Fish Movement** (`state.level.upgrades.fishMovement`, 0-5, costs `FISH_MOVEMENT_UPGRADE_COSTS`): adds `FISH_MOVEMENT_UPGRADE_SPEED_BONUS` (5 px/sec) per level on top of a species' `swimSpeed`. Every `SPECIES` row in `Config.js` already has this exact amount subtracted from its originally-tuned speed, so buying Level 1 restores the "real" speed and Level 2-5 push past it — un-upgraded, every species swims 5px/sec slower than its balance-tuned value, which is intentional (see each row's inline comment). Applied live via `Entities.js`'s `effectiveSwimSpeed(def, state)`, read everywhere movement is computed (`createFish`'s initial velocity, `wander`, and the hunger-seek speed) rather than baked in once, so a mid-playthrough purchase speeds up every fish already in the tank on their very next wander/seek recompute, not just future spawns.
- **Food Capacity** (`state.level.upgrades.foodCapacity`, 0-5, costs `FOOD_CAPACITY_UPGRADE_COSTS`): caps how many food pellets can exist in `state.level.items` at once — `FOOD_MAX_ON_SCREEN_BASE` (2) plus `FOOD_CAPACITY_UPGRADE_INCREMENT` (2) per level, so 2 → 4 → 6 → 8 → 10 → 12 at max level. Enforced in `Entities.js`'s `trySpawnFood` (`effectiveFoodCapacity(state)` computes the live cap; spawning is refused past it regardless of money, the same kind of hard gate as insufficient funds) — deliberately tight at base level so early feeding is a real logistical constraint (wait for pellets to be eaten/despawn before dropping more) rather than something the player can spam freely.
- **Defensive Capabilities** (click damage/offense vs. alien waves): shown as a fourth card in the panel shell (Phase 2 UI scope, per the design update) but locked/non-interactive — there's no alien system to upgrade yet (Phase 5). Wiring this up is explicitly Phase 5+ scope, tied to whatever combat direction that future design pass settles on (see Species Roster & Progression's Phase 5+ note).

All three trees are simple linear ladders (`*_UPGRADE_COSTS` arrays in `Config.js`, index 0 = cost of level 1) — placeholder balance, tune once real playtesting exists, same as every other economy constant in this file.

## Items can't stack, and can fall off the bottom

Two design changes to seabed item physics, both aimed at the same problem: without them, a single Collector tile could just absorb an unlimited stream of coins forever, and any coin that missed one just sat at the world's bottom waiting to be clicked by hand — neither made routing infrastructure (ramps, multiple Collectors, spreading a stream out) actually necessary. Both are pure `Grid.js`/`Entities.js` physics; nothing about tile placement or the Mound/Tank Points systems above changed.

**No floor at the world's bottom (`Grid.js`'s `tileAt`):** out-of-bounds reads off the *left/right/top* edges of the world still return `TILE_WALL` (nothing needs to fall off the sides), but reads below `WORLD_TILES_H` now return `TILE_EMPTY` instead — there's deliberately no implicit floor down there any more. An item that reaches it just keeps falling; `stepItemOnGrid` checks for this before anything else and returns a new `'lost'` status once the item has fallen `ITEM_LOST_BELOW_WORLD_MARGIN_PX` past `WORLD_H` (falls a little past the bottom edge first, so the loss reads as "fell off the bottom of the screen" rather than popping out of existence at an invisible line). Entities.js's callers all remove the item on `'lost'` with no payout; coins additionally get a small "Lost!" floating text (`ITEM_LOST_COLOR`) planted at `(item.x, WORLD_H)` — not the item's actual, long-since-off-screen position — so a player watching the bottom edge sees *why* it vanished. Food/waste vanish silently (food already had no such feedback; waste disappearing into the void is arguably a convenient way to get rid of it).

**Items can't overlap, and nothing is ever permanently anchored (`Grid.js`'s `resolveItemCollisions`):** the first version of this made a pile "settle and freeze" — once an item was marked resting it was never simulated again, so a pile just sat there immune to gravity and immune to being pushed, which read as items snapping into a fixed structure rather than behaving like coins. Per direct playtest feedback ("they aren't affected by gravity when settled... they need to behave more like particles of liquid pushing each other around, rather than stickers that get stuck in weird structures"), this was replaced with a model where **every seabed item is stepped every tick for as long as it exists, whether it's currently resting or not** — there's no one-way "stop simulating this" state anywhere in the pipeline:
- `resting`/`restingOnFloor` are purely informational booleans, re-evaluated fresh from `stepItemOnGrid`'s return value every single tick (`Entities.js`'s `updateCoin`/`updateWaste`/`updateFood` — `item.resting = status === 'resting'`, not a one-way flip). An item that was resting last tick but got shoved off its support this tick immediately reports `'falling'` again and gravity picks it right back up, the same as if the tile under it had been removed.
- `resolveItemCollisions` (`Grid.js`) runs once per tick from `Entities.js`'s `updateEntities`, after every item's individual tile-physics step — comparing every seabed-band item (`item.y >= SEABED_FLOOR_Y`) against every other one, not just against tiles. It runs `ITEM_COLLISION_ITERATIONS` (4) sub-passes per tick so a push at the top of a stack can propagate down through several layers within a single tick, rather than one layer per tick.
- Resolution combines two things applied symmetrically to *both* items in an overlapping pair (no "anchor" side any more): a direct positional correction along the center-to-center line (guarantees no overlap remains immediately after — what keeps this stable no matter how deep a pile gets) plus a small velocity kick (`ITEM_PUSH_IMPULSE_SPEED`) so a shoved item keeps visibly drifting for a moment instead of snapping into place and stopping dead. `ITEM_HORIZONTAL_DAMPING` (0.82/tick, applied in `stepItemOnGrid`) is what brings that drift back to a natural stop rather than oscillating or running away forever. `ITEM_PUSH_IMPULSE_SPEED` is deliberately small (3, down from an initial 20) — at the higher value, a steady stream of coins landing near the same spot could each add enough sideways (and, since the push direction always carries some vertical component too — see the vertical-fraction cap below — upward) velocity that gravity couldn't pull a freshly-arrived coin back down to the pile's actual resting height before the next one landed, producing a visibly unnatural diagonal "staircase" of coins marching up and off the edge of whatever they were piled on instead of settling flush in a row. The positional correction alone (bounded by actual overlap depth, so it can't run away) is what actually guarantees non-overlap; the impulse is now just enough residual motion to read as a gentle settle.
- Both the positional correction and the velocity kick are weighted by relative mass (`item.mass`, an explicit field set at creation — see `ITEM_MASS_BY_TYPE` below — not derived from radius): the heavier item's fraction of the push is the *lighter* item's mass over the total, so a heavy coin barely moves while a light food pellet gets shoved well clear. Both halves have to be weighted, not just the position — the velocity kick dominates a multi-tick shove far more than the one-shot positional correction does, so an early version that mass-weighted only the position still let a coin drift sideways almost as far as the food pellet that hit it.
- `pushDirection` uses the *true* center-to-center angle whenever it already has a meaningful horizontal component, so an item rolls toward whichever side it's actually leaning, proportional to how far off-center it landed — a 2%-off-center landing and a 40%-off-center landing resolve differently, not identically. Only a landing close enough to dead-center to be a genuine unstable-equilibrium case (no real lean at all, which would otherwise balance on the peak forever — a real coin wouldn't actually hold that, but the simulation has no physical noise to break the tie with) gets a small fixed nudge substituted in via `ITEM_MIN_HORIZONTAL_PUSH_FRACTION` (0.15), just enough that nothing perfectly stacks. An earlier version instead *clamped* every landing whose vertical component exceeded a threshold down to one fixed diagonal regardless of true offset, which read as items sliding along a fixed-angle "flat ceiling" instead of rolling proportionally to where they actually landed.
- The positional correction is additionally capped per pairwise resolution by `ITEM_MAX_PUSH_PER_STEP` (3px), regardless of how deep the true overlap is. Two coins spawned at (almost) the exact same spot — a tight fish swarm dropping coins on top of each other in open water, where nothing separates them until they cross into the seabed band together — can arrive already overlapping by nearly their full diameter; resolving that in one uncapped shot could reposition a coin far enough to cross back above `SEABED_FLOOR_Y` into open water, where it then free-falls under the open-water gravity branch with whatever velocity it had, reading as a coin launching itself out of the pile into the water for no reason. Clamping the per-call correction means a severe overlap just takes a few extra ticks (still resolved within well under a second, since `resolveItemCollisions` reruns every tick) instead of teleporting.
- Landing on top of *another item* (as opposed to a tile) clamps that item's `vy` down to `ITEM_ON_ITEM_LANDING_VY_CAP` (24px/s) instead of leaving it alone. `sweepVertical` already zeroes `vy` the instant an item lands on a solid *tile*, but nothing did the equivalent for item-on-item contact — and `stepItemOnGrid`'s gravity integration runs unconditionally every tick regardless of resting status (see its module comment), so a coin resting on top of another coin had its `vy` climb under gravity every single tick, each time caught by a full-strength positional correction: a genuine "impact" every tick, forever. That was the dominant cause of coins visibly bumping/sliding along the top of a pile instead of settling — worse than the angle issue above. The fix isn't a hard zero, though: a first attempt at exactly that made re-penetration per tick (and thus the corrective roll-off) so tiny — under 0.03px — that an off-center landing took upward of 20 simulated seconds to visibly finish rolling off, reading as "stuck" rather than settled. A capped-but-nonzero residual fall speed keeps the roll-off brisk (under ~2 seconds) while staying far enough below `MAX_FALL_SPEED` that it can't regenerate a large, `ITEM_MAX_PUSH_PER_STEP`-clamped overlap the way an unclamped full-speed fall did.

`ITEM_MASS_BY_TYPE` (`Config.js`) is `{ food: 0.3, coin: 3, waste: 1 }`, with a coin's mass additionally scaled by its value tier's `sizeMultiplier` (a diamond coin is heavier than a bronze one, same scale as its size).

Verified via direct Node sims (a resting item resumes falling the instant its support tile is removed — confirms no permanent anchoring; dropping a second coin onto an already-resting one visibly displaces it while staying non-overlapping; a pile of coins crowded onto a narrow 3-tile platform pushes at least one off the edge and it falls past the platform, propagating through the stack; a coin barely moves when it collides with food while the food gets shoved roughly 10x as far, matching the mass ratio; a 40-item stress pile over 10 simulated seconds produces no NaN positions and no runaway drift; an item with nothing built anywhere still falls off the bottom of the world and reports `'lost'`) and end-to-end in a browser (a Dartfin swarm dropping coins onto a wall strip with one Collector tile in the middle spreads coins into a continuous non-overlapping row across the strip rather than stacking, with only coins actually landing on the Collector auto-banked — the rest pile up and have to be clicked or routed by hand).

## Coordinate system & world constants

All defined in `Config.js`, consumed everywhere else — never hardcode these elsewhere.

- `TILE_SIZE = 32` px
- `WORLD_TILES_W = 160`, `WORLD_TILES_H = 45` → world is `5120 x 1440` px
- Water column: tile rows `0..26` (27 rows)
- Seabed grid: tile rows `27..44` (18 rows)
- `SEABED_ROW_START = 27` — the authoritative source for the water/seabed boundary; Phase 1 renders this as a flat floor, Phase 2 replaces it with real tiles, but both read this same constant

**Rule:** gameplay logic never operates in screen coordinates. `Engine.js` exports `worldToScreen(x, y)` and `screenToWorld(x, y)`; all input hit-testing and all rendering go through them. Entities outside the camera view are culled before drawing.

## Fixed-timestep contract

`requestAnimationFrame` drives rendering only. Simulation advances on a fixed 60Hz accumulator (`SIM_DT_MS = 1000/60` in `Config.js`) with a max-frames-per-update clamp so a tab stall doesn't spiral. Any physics/gravity/collision code reads `SIM_DT_MS`, never the rAF delta — this matters starting Phase 2 when gravity meets grid tiles (variable delta = tunneling).

`state.debug.timeScale` (1/2/5/10/0) multiplies how many fixed steps run per rAF frame; it does not change `SIM_DT_MS` itself.

## Module responsibilities

- **main.js** — entry point. Owns the root `state` object's initial shape. Calls into `Levels.js` to load the first level through the real load path. Wires the rAF loop to `Engine.js`. **Forbidden:** no gameplay logic, no direct entity manipulation.
- **Engine.js** — fixed-timestep accumulator loop, camera (position/zoom/clamping/pan input), raw input handling (keyboard/mouse state), `worldToScreen`/`screenToWorld`. **Forbidden:** no knowledge of fish/items/grid contents; it moves the camera and hands out coordinates, nothing more.
- **Entities.js** — `Fish` (species-table-driven), `Alien`, `Food`, `Item` (coin/waste/science). Owns `state.level.entities` and `state.level.items` contents and their per-tick behavior; also awards `state.level.tankPoints` on fish adult-growth transitions and writes the one-time Tank Points tutorial line to `state.level.notifications` (see Tank Points & Tank Upgrades). **Forbidden:** no rendering (that's UI/main render pass), no tile placement.
- **Grid.js** — seabed tile array, gravity/slope physics for items once they reach the seabed, ramp/blaster/collector routing, and item-item collision (`resolveItemCollisions` — see "Items can't stack, and can fall off the bottom"). Owns `state.level.grid`. **Forbidden:** no fish logic, no camera math.
- **Mound.js** — the Mound: click hit-testing (`isPointOnMound`), `crackMound()` (spends money, advances `state.level.tier`, grants that tier's unlocks into `state.meta`, writes to `state.level.notifications`), and its own render. Does **not** own the "Throw money at it" popup itself — that's a DOM modal in `UI.js` (`openMoundMenu`/`closeMoundMenu`), which `crackMound()` gets called from. **Forbidden:** no per-tick simulation of its own (it's a click target plus a render, not something that ticks every frame like Systems.js will).
- **Systems.js** — cleanliness/toxicity, eel power balance, science accumulation, wave timers. Cross-cutting simulation systems that read/write multiple parts of `state.level` (and `state.meta.scienceTotal`). **Forbidden:** no rendering, no input handling.
- **UI.js** — shop panel, Tank Upgrades panel (Phase 2 — see Tank Points & Tank Upgrades), the Mound's "throw money" popup, sidebars, tech tree modal, debug overlay rendering. Reads state, writes only via explicit user actions (buy, place tile, toggle debug). **Forbidden:** no simulation logic (e.g. UI must not tick hunger or move items).
- **Levels.js** — `LEVELS` data array, level load/unload (rebuilds `state.level` from scratch, never touches `state.meta` except to grant rewards on completion), win/lose condition checks.
- **Config.js** — all constants, balance numbers, the `SPECIES` table, world/tile constants, `SIM_DT_MS`. Pure data, no logic. Every balance constant carries a comment explaining its pacing intent.

**Item collision physics rewritten from "settle and freeze" to continuous granular physics**, directly in response to playtest feedback that the first version wasn't behaving like real coins — a formed pile was immune to gravity and immune to being pushed once marked resting, which read as items snapping into a fixed structure. Fixed by removing every early-return-if-resting gate in `Entities.js`'s `updateCoin`/`updateWaste`/`updateFood` (`resting`/`restingOnFloor` are now re-evaluated fresh every tick instead of one-way flips) and rewriting `Grid.js`'s `resolveItemCollisions` so every seabed item is compared against every other one every tick regardless of resting status, with pushes weighted by an explicit `item.mass` field (`ITEM_MASS_BY_TYPE` in Config.js — food is ~10x lighter than a coin) rather than the old radius approximation — see "Items can't stack, and can fall off the bottom" above for the full mechanism, including the `MAX_SETTLE_ATTEMPTS`/`justSettledThisTick`/`findClearSettlePosition` machinery that got deleted entirely along with the one-way settle model. One bug caught during verification: the positional correction was mass-weighted from the start, but the velocity impulse (`ITEM_PUSH_IMPULSE_SPEED`) initially wasn't, so a heavy coin still drifted almost as far sideways as a light food pellet it collided with, since the repeated-every-tick velocity kick dominates a multi-tick shove far more than the one-shot position correction does — fixed by weighting the impulse by the same mass fraction. Verified via direct Node sims (11/11 passing: no permanent anchoring — a resting item resumes falling the instant its support is removed; dropping a coin on a resting one visibly displaces it while staying non-overlapping; a crowded narrow platform pushes an edge item off entirely, confirming a push propagates through a stack; a coin moved ~1.76px against food's ~18.5px in a head-on collision, confirming the ~10x mass ratio actually reads through; a 40-item stress pile over 10 simulated seconds produced no NaN/runaway positions; world-bottom loss still works) and end-to-end in a browser (a Dartfin swarm over a wall-strip-plus-Collector spread coins into a continuous non-overlapping row rather than stacking, zero console errors). Full existing regression suite (restart, pause/collapse, species-unlock) still passes unchanged.

**Follow-up tuning pass on the same system**, per direct playtest feedback on a screenshot showing coins landing on a wall strip forming a visibly unnatural diagonal staircase climbing up and off the platform's edge instead of settling into the row: `ITEM_PUSH_IMPULSE_SPEED` was cut from 20 to 3 (see that constant's comment in Config.js). At 20, a steady stream of new coins landing near the same spot could each add enough velocity — including a forced vertical component, since `pushDirection`'s vertical-fraction cap means a near-dead-center landing is never resolved as purely horizontal — that gravity couldn't pull a freshly-arrived coin back down to the pile's actual height before the next one landed, so each new arrival ended up resting progressively higher and further over than the last. The bounded positional correction (not the velocity impulse) is what actually guarantees non-overlap, so shrinking the impulse doesn't reopen the original stacking problem — verified by a direct Node sim dropping 15 coins one at a time onto the same spot on a long strip: every coin now settles at exactly the same height (0px vertical deviation) in a tight single-file row centered on the drop point, and a repeat of the narrow-3-tile-platform stress test still successfully knocks an edge coin off, confirming push propagation through a stack still works. End-to-end in a browser: a swarm of Dartfin parked over a deliberately too-short 5-tile strip (guaranteed overflow) produced 8 coins sitting flush in a single row with zero staircase, zero console errors. Full existing regression suite still passes unchanged.

**Second follow-up: a screenshot showing coins airborne near the Mound, well above the seabed**, per feedback that coins would still occasionally shove themselves "way more than the coins under it, which isn't how gravity works." Root cause was different from the staircase bug: `resolveItemCollisions`'s positional correction was sized directly off the true overlap depth (`minDist - dist`) with no cap. A tight fish swarm parked over one spot drops multiple coins that can spawn at (almost) the exact same position and fall through open water in lockstep — nothing separates items above `SEABED_FLOOR_Y`, since `resolveItemCollisions` only ever looks at the seabed band — so by the time they cross into the seabed band together they can be overlapping by nearly their full diameter. Resolving that much overlap in one shot flung a coin far enough to cross back above the seabed line into open water, where it then continued as a free ballistic projectile under the open-water gravity branch, looking exactly like a coin launching itself out of the pile for no reason. Fixed by adding `ITEM_MAX_PUSH_PER_STEP` (3px) and clamping the per-pairwise-resolution `overlap` to it before computing the correction — a severe overlap now just takes a few extra ticks to visibly separate instead of teleporting (see "Items can't stack" above for the mechanism). Verified via a direct Node sim spawning 8 coins at sub-pixel-apart positions directly in the seabed band (the worst case): max single-tick vertical movement stayed at 1.2px (matching ordinary free-fall speed, not a jump), no coin ever crossed back above the seabed line after landing, and all 8 settled into a flush non-overlapping row — plus the existing narrow-platform and mass-asymmetry tests still pass, confirming the clamp didn't reopen either prior fix. End-to-end in a browser, a dense 12-Dartfin swarm packed tightly over a wall-strip-plus-Collector (the same scenario that originally produced the airborne-coins screenshot) produced two clean flush rows with nothing airborne, zero console errors. Full existing regression suite still passes unchanged.

**Third follow-up: coins visibly sliding/bumping along the top of a pile "as if moving across a flat ceiling"** instead of rolling naturally into gaps. Two compounding root causes, both in `Grid.js`: (1) `pushDirection` *clamped* every landing whose vertical component was steep enough down to one fixed diagonal (`ITEM_MAX_VERTICAL_PUSH_FRACTION`, 0.6) regardless of true offset — a 2%-off-center landing and a 40%-off-center landing resolved identically, which is what actually produced the "same fixed angle every time" flat-ceiling look; and (2) more significantly, `sweepVertical` only ever zeroes an item's `vy` when it lands on a solid *tile* — nothing did the equivalent for landing on *another item*, and `stepItemOnGrid`'s gravity integration runs unconditionally every tick (by design, so nothing is ever permanently anchored — see above), so a coin resting on top of another coin had its `vy` climb under gravity every tick, each time caught by a full-strength positional correction: a genuine "impact" every single tick, forever. Fixed both: `pushDirection` now preserves the true angle and only substitutes a small fixed nudge (`ITEM_MIN_HORIZONTAL_PUSH_FRACTION`, 0.15) for the genuinely near-dead-center case, so off-center landings roll proportionally instead of snapping to a fixed diagonal; and item-on-item landings now clamp (not zero) `vy` via `ITEM_ON_ITEM_LANDING_VY_CAP` (24px/s). A hard zero was tried first and made things worse in a different way — re-penetration per tick dropped to under 0.03px, so a near-center landing took upward of 20 simulated seconds to finish rolling off, reading as "stuck" rather than settled; the capped-but-nonzero version settles the same landing in under 2 seconds. Verified via direct Node sims (14/14 passing, including two new cases: a coin dropped dead-center on top of another now fully settles and stops creeping within ~2 simulated seconds and stays put for 5+ seconds afterward with zero further drift, and two coins built at a fixed overlap depth but different approach angles resolve with proportionally different horizontal movement — 0.454px at a shallow angle vs 0.891px at a steep one, not identical) plus every prior regression (no permanent anchoring, narrow-platform knock-off, mass asymmetry, coincident-spawn teleport safety, stress-pile stability, world-bottom loss) still passing, some needing longer tick budgets since the gentler physics settles over more ticks rather than fewer, larger corrections. End-to-end in a browser, the same dense-swarm scenario produced two clean flush rows, zero console errors, and noticeably more items successfully routed through the Collector than before (10 vs 4-5), consistent with piles settling into gaps more reliably instead of getting stuck skittering. Full existing regression suite still passes unchanged.

**General de-pacing pass, per direct request to slow the game down through strategic changes** (not a bug fix, a balance pass): `FOOD_GRAVITY`/`FOOD_MAX_FALL_SPEED` cut another 25% (44→33, 36→27, stacking on top of the earlier 20% cut noted in Config.js's comments — food now falls noticeably more slowly, giving fish and the player more time to react/aim), `FOOD_QUALITY_SINK_SPEED_REDUCTION_PER_LEVEL` doubled from 5% to 10% per Tank Upgrade level (so that upgrade now meaningfully slows food further rather than being a marginal tweak), and every species' `hungerRate` cut 20% (all 18 rows in `Config.js`, base feeders and hybrids alike) so fish need feeding less frequently across the board.

Also rebalanced the base 3 feeders' coin-value growth curve, since the *effective* $/sec income (dropValue ÷ dropInterval, what a player actually perceives) was climbing 4-6x from hatchling to adult even though the raw `dropValue` numbers alone only looked like ~2-2.6x — the extra multiplier was hiding in each stage's `dropInterval` also shrinking. Baby `dropValue` is unchanged for all 3 (Guppy $5, Dartfin $3, Blimpfish $16); mid/adult values were brought down so the *effective* income ratio lands close to double instead: Guppy is now flat at `5, 5, 5` (its own `dropInterval` shrink alone already delivers a ~1.9x income ratio, so no dropValue growth was needed at all), Dartfin similarly flat at `3, 3, 3` (~2.4x from interval shrink alone), and Blimpfish — whose interval alone only shrinks the income ratio ~1.4x — got a modest dropValue bump to `16, 17, 22` to reach a comparable ~2.0x. This is also why the 9 feeder-based hybrids' `dropValue` (1.2x their feeder parent's *adult* value — see the new Gene-Splicing note above) reads lower than before: Guppy-based hybrids dropped from 7 to 6, Dartfin-based from 3 to 4 (a rare increase, since old Dartfin-hybrid values predated this rebalance entirely and happened to sit below the new 1.2x-of-adult formula), Blimpfish-based from 20 to 26.

**Ramps reworked from a fixed-speed diagonal slide into a pass-through nudge, and the Blaster's launch got an angle**, both per direct feedback and both documented in full under "Ramps ('funnels')" and "The Blaster" above. Ramps no longer arrest vertical motion at all (removed from `Grid.js`'s `SOLID_TILES` entirely) — an item falling or rising through one keeps its `vy` completely untouched and just gets shifted one tile sideways (`RAMP_NUDGE_DISTANCE`) as it passes through that row, replacing the old `item.slidingRamp`/`stepRampSlide` mechanism (deleted) that rode a fixed `RAMP_SLIDE_SPEED` 45-degree slope and read as a sticky conveyor belt. The Blaster's launch now splits its speed into a vx/vy pair by up to `BLASTER_LAUNCH_ANGLE_MAX_DEG` (7°) based on exactly where across the tile the item landed, rather than a pure vertical shot — which surfaced a real pre-existing gap: `Entities.js`'s open-water branch for coins/waste only ever integrated `item.y`, never `item.x`, so a nonzero `vx` had zero visible effect for the majority of a Blaster's arc (which typically leaves the seabed band). Fixed by adding `item.x += item.vx * dt` to both open-water branches. Both tiles also got a matching visual pass: Ramps render as a triangle pointing the direction they push (`Grid.js`'s `renderTileShape`, replacing the plain square every building used to share) and the Blaster's top two corners are now slightly rounded (`BLASTER_TOP_CORNER_RADIUS_FRACTION`), bottom left square since it still sits flush on whatever's underneath it. Verified via 10 direct Node sim tests (a falling item's vy is provably unchanged crossing a Ramp row while landing one tile over; a rising item off a simulated Blaster launch behaves the same way; lingering in the same Ramp row for 30 ticks only ever nudges once, not every tick; a dead-center Blaster hit launches with ~0 horizontal velocity; a hit near the tile's edge tilts within the ±7° band; launch speed magnitude is identical regardless of angle, only direction changes) plus the full existing regression suite. End-to-end in a browser: tile shapes render correctly (left/right wedges, rounded-top Blaster) and a Dartfin parked over a Blaster visibly arcs sideways on repeated launches instead of retracing the same vertical line, zero console errors.
